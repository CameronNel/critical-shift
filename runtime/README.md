# Critical Shift runtime foundation (WP-01)

This is the minimal engine foundation, not a playable Critical Shift build.
It deliberately does not load, convert or modify the authored Blender map.
Native acceptance and independent review must be established from actual evidence.
See [the task and gate record](validation/WP01.md) and the existing
[architecture authority](../design/code-architecture/README.md).

## Open and run

Use Unity **6000.4.3f1**, revision **39d1a88d4dd1**, with an activated license.
Add `runtime/unity/` as the project in Unity Hub. After import, choose
**Critical Shift > Foundation > Prepare project**. This native editor command
creates the one-camera diagnostic startup scene and serializes the standalone
profile. Open `Assets/CriticalShift/Bootstrap/Foundation.unity` and press Play.
The small diagnostic panel is an engineering fixture, not approved game UI/art.
The test suites are in the Test Runner under EditMode and PlayMode.

The first-party source and GUID metadata are checked in. The initial scene and
full ProjectSettings are generated by the pinned Editor, not fabricated YAML.
They are deliberately pending native generation/verification. The automated
runner captures these in its disposable workspace once the editor can execute.
This distinction means the current source bootstrap alone is not a completed WP-01.

## One-command native validation

Close the editor before validating. Python 3.12 or newer is required.
From the repository root, use the executable for an **already activated** editor:

```powershell
python runtime/tools/run_foundation.py --unity "C:\Program Files\Unity\Hub\Editor\6000.4.3f1\Editor\Unity.exe" --target Win64
```

```sh
python3 runtime/tools/run_foundation.py --unity /path/to/6000.4.3f1/Editor/Unity --target Linux64
```

The command copies only the small runtime source into a fresh directory under
`runtime/out/`, runs prepare/import, all 12 expected EditMode tests, both PlayMode
tests, builds a minimal Development Player, then starts it with `--cs-smoke`.
The Player must emit its matching build identity, run at least 12 frames and
shut down normally with zero reported errors. The default product window remains
open until closed when `--cs-smoke` is absent. No interactive gameplay is implemented.

Each run has new XML/log/output paths. A prior green result cannot be reused.
`report.json` records individual phase states, the input hash and source-preservation
check. Exit codes: **0** all implemented native checks passed, **1** failure,
**2** prerequisite blocked. A passing WP-01 run still needs independent review;
WP-02 and the rest of Gate 0 are not automatically satisfied.

No Unity account details or license files belong in Git or chat. Use your normal
Unity Hub activation on your own machine. The hosted workflow does not invent a
license or silently skip the native requirement. A license failure leaves that
job non-green and the gate blocked while preserving the report.

## Source and supplementary checks

```sh
python3 runtime/tools/check_source.py
python3 -m unittest discover -s runtime/tools/tests -v
```

The source checker checks metadata pairs/uniqueness, direct assembly ownership,
version consistency and the one pure assembly. It is not WP-02's resolved-graph
checker. Negative-control tests verify result gating, build-identity matching,
source-copy safety and zero-test/skip/error rejection.

The optional hosted check downloads the official pinned editor and NUnit package,
verifies their published integrity metadata, and uses .NET SDK **8.0.423** to compile
five source files against the **real Unity references**, with warnings as errors.
It also executes the eight synchronous process-lifetime tests using the actual
Unity-supplied NUnit assertion library in a narrow standalone .NET harness.
**Neither check is Unity EditMode/PlayMode, native import, physics or a Player run.**
The supplementary toolchain is not a runtime gameplay dependency.

## Ownership and scope

`CriticalShift.Application` contains only process-lifetime transitions. A new
instance starts Created, becomes Ready explicitly and stops idempotently. It is
not the future shift/session/worker/gameplay state owner.
`CriticalShift.Bootstrap` owns local process construction and diagnostic readiness.
The Editor assembly owns project preparation/validation and building; test code
has separate test assemblies. No singleton, global service bus or empty feature
catalogue is introduced. No networking, input/UI framework, Steam, voice, save,
reactor or mine integration is selected. IMGUI is used solely for the diagnostic
fixture and is already a Test Framework dependency.

Only the foundation scene is registered for builds. Existing source art, logical
mine IDs, section bindings and `MAP.json` remain outside the runtime import scope.
